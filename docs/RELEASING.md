# Archiving this repository on Zenodo and getting a DOI

This guide takes the repository from a local working copy to a citable archive
with **two** DOIs: a *concept* DOI for the project and a *version* DOI for the
`v1.0.0` snapshot.  Steps 3 and 4 are order-sensitive: Zenodo's GitHub
integration must be switched on **before** the GitHub release is created,
otherwise the release is not archived.

## 1. Create the GitHub repository

1. Create a public repository, e.g. `suzuki-hte-benchmark` (public is required
   for the free Zenodo GitHub integration).
2. Do **not** commit the raw datasets (they are not redistributed), `.venv/`,
   `outputs/` or `__pycache__/`.  The shipped `.gitignore` already covers these.
3. Confirm the payload includes `setup_env.bat` (venv + dependencies in one click) and that:
   `scripts/`, `hte/`, `tests/`, `docs/`, `archive/`, `scripts/`, `hte/`, `tests/`, `docs/`,
   `archive/`, `data/alias_mapping.yaml`, `data/col_mappings.csv`,
   `results/legacy/` (the two inputs `bootstrap_ci.py` needs), `requirements.txt`,
   `LICENSE`, `LICENSE-DATA`, `CITATION.cff`, `README.md`, `README.zh-CN.md`.
   `results/`, `outputs/` and `figures/` are **generated by `run_all.bat`** and are not
   part of the payload.

## 2. Push the code

```bash
git init
git add .
git commit -m "v1.0.0: HTE yield-prediction benchmark"
git branch -M main
git remote add origin https://github.com/<user>/suzuki-hte-benchmark.git
git push -u origin main
```

Check on GitHub that `archive/single_dataset_full_benchmark.py` is byte-identical to
the local copy and that `results/checksums.txt` matches the shipped files
(`sha256sum -c` on Linux/macOS, or compare the hashes by hand on Windows).

## 2b. Running two pipelines at once (the machine-wide lock)

Every entry point honours one lock file, `.pipeline_owner.json` in the repository root.
**It is off by default**: since the package moved to the CPU-only `xgboost-cpu` wheel,
two concurrent runs finish with identical numbers, so the lock is only needed when you
want to protect the machine from CPU contention.

| Command | Effect |
|---|---|
| *(nothing)* | Lock **off**.  Two datasets may run at once. |
| `set CD_LOCK=1` | Lock **on** for that console: a second `run_all.bat` / `Single_dataset_full_benchmark.bat` exits with code **3** and prints the holder (`pid=…, kind=…, started …`). |
| `python scripts\pipeline_lock.py status` | Print whether a run is in progress. |
| `python scripts\pipeline_lock.py acquire --kind run_all --ttl-minutes 360` | Take the lock by hand (exit 3 = busy). |
| `python scripts\pipeline_lock.py release --force` | Clear a lock left behind by a killed run.  A `run_all` lock also expires on its own after its TTL, so this is only needed to start sooner. |

The single-dataset script additionally takes a Windows named mutex, which the kernel
releases when the process dies; the batch runs rely on the file and its TTL.  Both sides
read the same file, so a dataset run and a batch run never overlap while `CD_LOCK=1`.

## 3. Enable the Zenodo GitHub integration (BEFORE the release)

1. Sign in at <https://zenodo.org> with the GitHub account that owns the repo.
2. Open **Settings -> GitHub** (<https://zenodo.org/account/settings/github/>)
   and authorise Zenodo if prompted.
3. Find `suzuki-hte-benchmark` in the repository list and flip its switch **on**.
4. Optional but recommended: use <https://sandbox.zenodo.org> first to rehearse
   the flow without minting a real DOI.

Zenodo only archives releases created **after** the switch is on.  A release
that already existed when you enabled the integration has to be edited and
re-published to be picked up -- which is why this step comes before step 4.

## 4. Create the `v1.0.0` release

1. On GitHub: **Releases -> Draft a new release**.
2. Tag: `v1.0.0` (create the tag from `main`).  Title: `v1.0.0`.
3. Paste release notes (what the code reproduces, the frozen-pipeline sha256,
   the fact that raw data are not included).
4. **Publish release**.
5. Wait for the Zenodo webhook (usually seconds to a few minutes).  A new
   Zenodo record appears, with files and a DOI.

## 5. Retrieve BOTH DOIs

On the Zenodo record page:

* **Version DOI** -- shown in the record's DOI field / "Cite this version",
  e.g. `10.5281/zenodo.1234567`.  It always refers to `v1.0.0` exactly.
* **Concept DOI** -- shown as "Concept DOI" / "Cite all versions",
  e.g. `10.5281/zenodo.1234566`.  It always resolves to the **latest** version.

Both are on the record; copy both and keep them with the release notes.

## 6. Add the badge to `README.md`

The README already has a placeholder badge:

```markdown
[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.XXXXXXX.svg)](https://doi.org/10.5281/zenodo.XXXXXXX)
```

Replace `XXXXXXX` with the **concept DOI** suffix (the badge then always points
at the newest version):

```markdown
[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.1234566.svg)](https://doi.org/10.5281/zenodo.1234566)
```

If the badge must point at the `v1.0.0` snapshot instead, use the version DOI.
Also remove the "placeholder" note below the badge and update `CITATION.cff`
(`doi:` and `version:`) with the version DOI.

## 7. Which DOI to cite where

| Where | DOI | Why |
|---|---|---|
| Academic CV / personal website / "software" list | **Concept DOI** | Stable forever; always resolves to the newest archived release. |
| Paper's data-availability statement | **Version DOI** | Pins exactly the code that produced the published numbers. |

Example data-availability sentence:

> Code and result tables are archived at Zenodo,
> doi:10.5281/zenodo.1234567 (version v1.0.0).  The concept DOI
> 10.5281/zenodo.1234566 always resolves to the latest release.

## 8. Later releases

Publishing a new GitHub release (e.g. `v1.0.1`, `v1.1.0`) makes Zenodo mint a
**new version DOI** for that snapshot.  The **concept DOI never changes**, so
links that use it keep working.  Only the version DOI in the paper's
data-availability statement is version-specific; cite the new version DOI there
if the code changes in a way that affects the published numbers.

## 1b. Build the uploadable zip in one command

```bash
python scripts/make_release.py --zip
```

It copies exactly the shipped payload (code + docs + `archive/` + `data/` mapping tables +
`results/legacy/` inputs) to `../repo_release/`, prints a `manifest sha256`, and writes
`../repo_release.zip`. `results/`, `outputs/` and `figures/` are **not** included: they are
produced by `run_all.bat`. `--dry-run` prints the manifest without copying.
